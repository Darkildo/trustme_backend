# Изменения

Версии ноды `trust_message_tcp`. Минорная версия растёт, когда меняется
наблюдаемое клиентом поведение или схема, патч — для исправлений без
такого изменения.

## 0.4.0 — не выпущена

### Доставка с подтверждением на прямом (sled) бэкенде

Раньше прямой бэкенд удалял офлайн-запись сразу после записи кадра в
сокет, а онлайн-кадр шёл в канал сессии с `messageId = 0` и терялся при
разрыве. Гибель процесса получателя между чтением и обработкой теряла
сообщение. Теперь — как у брокерного бэкенда:

- Конверт пишется в очередь получателя при приёме, в том числе для
  живого получателя, и лежит там до `DeliveryAck` клиента той же области
  (account-запись — любая сессия аккаунта, запись устройства — только
  сессия этого устройства). `IncomingMessage.messageId` ненулевой и при
  онлайн-доставке.
- Неподтверждённое выдаётся снова: той же живой сессии через
  `SLED_ACK_WAIT_SECS` (30 с) и следующей сессии сразу при подключении.
  Каждая сессия при подключении читает свои очереди, а не только первая
  сессия пользователя или устройства.
- Окно неподтверждённых на сессию — `SLED_MAX_UNACKED_PER_SESSION` (1024);
  полное окно откладывает выдачу и не выписывает сессию. Внутри очереди
  уведомления не обгоняют бэклог.
- Повторы по умолчанию не ограничены (`SLED_MAX_DELIVERIES=0`), как у
  брокера. Ненулевой предел — ручка для клиентов без `DeliveryAck`:
  выдача с этим номером последняя и удаляет запись после записи в сокет
  (`1` — прежнее поведение). Только для старых клиентов; с клиентами
  trust_utils небезопасно, если ставить — не ниже 10 (клиентский карантин
  `UNACKED_REDELIVERY_LIMIT=5` сбрасывается при реконнекте). Неудачи
  (дерево `delivery_failures`) считаются только доказанные: клиент
  подтвердил выданное позже (по номеру первой выдачи в сессии) либо
  прислал кадр после выдачи, не прислав за всю сессию ни одного ack и
  прожив больше трёх `ack_wait`. Мёртвый сокет и необработанный хвост
  короткого пробуждения предел не расходуют.
- `TCP_USER_TIMEOUT_SECS` (120 с, Linux): полуоткрытый сокет, в который
  идут повторы, рвётся, и неподтверждённое уходит следующей сессии.
- `ServerConfig.supportsDeliveryAck = true` для прямого бэкенда, если
  хранение не выключено (`OFFLINE_MESSAGES_RETENTION=instant` — доставка
  только онлайн с `messageId = 0`, как раньше).
- `SendAck` для онлайн-доставки несёт `queueId = messageId` записи.
- Квоты очереди (`QUOTA_*`) применяются к любому приёму, в том числе для
  живого получателя: очередь хранит всё неподтверждённое. Под-квота пары
  отправитель→получатель для живого получателя поднята на
  `SLED_MAX_UNACKED_PER_SESSION`. Вердикт `FULL`
  кэшируется на секунду; метрика `queue_full_total{path}`.
- Снимок живых сессий для уведомления берётся после записи в очередь.
- `DELETED_MESSAGES_RETENTION` по умолчанию 7 суток вместо 30: в архив
  `meta` теперь попадает и онлайн-трафик (каждая подтверждённая запись).
- Повторная выдача пушей не порождает.
- Новые метрики: `sled_delivery_acked_total`, `sled_ack_timeout_total`,
  `sled_delivery_given_up_total`, `sled_window_full_total`;
  `message_redelivered_total` считает и повторы прямого бэкенда.

Протокол (`wire.proto`) не менялся, только комментарии. Формат записей
очередей прежний (v5); новое дерево `delivery_failures` создаётся само.

Требование к клиентам: подтверждать каждое `IncomingMessage` с ненулевым
`messageId` после сохранения, когда `supportsDeliveryAck = true`.
Дубликаты штатны (at-least-once), дедупликация — по `messageId` и
идентификатору внутри шифротекста.

## 0.3.0

аккаунта, очередь плюс устройство, отзыв сертификатов устройства.
