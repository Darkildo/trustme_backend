# Развёртывание ноды

Что нужно, чтобы поднять ноду и не потерять её ключ. Шаг «забрать ключ и
раздать клиентам» стоит раньше остальных: без него нода работает, но
подключиться к ней по IK никто не может.

---

## Что нужно знать заранее

**Клиент не может подключиться по IK, не зная ключа ноды.** Транспорт —
Noise IK, и ключ раздаётся вне полосы (конфигурация приложения, QR, ручной
пин). Путь первого контакта (Noise XX, TOFU) доверяет ключу, полученному
в момент подключения, — см. [runbook-node-key.md](runbook-node-key.md).

**Терять ключ нельзя.** Пустой том при рестарте означает новый ключ, и все
клиенты с пином отрезаны, хотя метрики доступности остаются в норме.
Обращение с ключом — [runbook-node-key.md](runbook-node-key.md).

## Требования

- Linux, x86-64.
- Диск под `STORAGE_PATH` — офлайн-очереди, push-токены, состояние
  планировщика пушей, реестр очередей, ключ ноды.
- Опционально NATS с JetStream (`DELIVERY_BACKEND=jetstream`).
- Для сборки — только Rust toolchain: схемы компилирует `protox` внутри
  `cargo`, `protoc` не нужен.
- Синхронизация времени (NTP): часы влияют на TTL сообщений, окна
  rate-limit'а и срок подписанного конфига — см.
  [runbook-failure-modes.md](runbook-failure-modes.md).

## Первый запуск

```bash
docker run -d \
  -p 5000:5000 -p 127.0.0.1:9000:9000 \
  -e BIND_PORT=5000 \
  -e METRICS_ENABLED=true \
  -v /srv/trust-message/data:/srv/trust-message/data \
  <образ>
```

1. **Забрать ключ из лога.**
   ```
   WARN generated a NEW node key ... node_key=<64 hex> node_identity_key=<64 hex>
   ```
   Клиентам нужен `node_key` — это X25519-статик. `node_identity_key`
   раздавать не нужно: клиент получает его в подписанном снапшоте и
   проверяет сам.
2. **Сделать бэкап секрета** (`STORAGE_PATH/node_identity_key`) или
   перенести его в `NODE_IDENTITY_KEY` из секрет-менеджера — см.
   [runbook-node-key.md](runbook-node-key.md).
3. **Раздать `node_key` клиентам.**
4. **Проверить, что нода отвечает и подпись конфига проверяется:**
   ```bash
   cargo run --release --example e2e_smoke -- \
     --message <host:port> --node-key <hex> --scenario probe_config
   ```

## Конфигурация: что решить до запуска

Полный список переменных — в [README](../README.md#конфигурация). Здесь —
те, где значение по умолчанию может не подойти.

| Переменная | По умолчанию | Когда менять |
|---|---|---|
| `NODE_IDENTITY_KEY` | — | Задать из секрет-менеджера: ключ переживёт пересоздание тома, потерю диска и переезд на другой хост |
| `DELIVERY_BACKEND` | `sled` | `jetstream` — доставка с `DeliveryAck` и передоставкой |
| `NATS_PUBLISH_TIMEOUT_MS` | `2000` | Короче — быстрее отказ при недоступном брокере; длиннее — только при заведомо медленной сети до NATS |
| `NATS_STREAM_MAX_BYTES` | 350 MiB | Объём потока. Политика `discard: old`: при переполнении молча вытесняются старые записи, включая недоставленные, поэтому занижать опаснее, чем завышать. Верхняя граница — свободное место под томом NATS |
| `LIMIT_HANDSHAKE_INFLIGHT_PER_IP` | `32` | **Поднять, если клиенты приходят через общий NAT или L4-балансировщик**: для ноды это один адрес |
| `NOISE_ALLOW_TOFU` | `true` | `false` в закрытом развёртывании: остаются только клиенты с пином |
| `SERVER_CONFIG_TTL_SECONDS` | `86400` | Короче — быстрее вступают в силу изменения конфига; длиннее — терпимее к рассинхрону часов |
| `ADVERTISED_ADDRESS` | пусто | Задать, если нода объявляет свой адрес клиентам |
| `OFFLINE_MESSAGES_RETENTION` | `30d` | Сколько хранить недоставленное на прямом бэкенде |
| `RATE_LIMIT_SEND_MSGS_PER_SEC`, `RATE_LIMIT_SEND_BYTES_PER_DAY` | `100`, 256 MiB | Если клиенты передают медиа частями, файл в десятки мегабайт — это сотни отправок подряд; лимиты нужно поднимать под реальный профиль |
| `PUSH_MIN_GAP_*_MS`, `PUSH_BURST_*`, `PUSH_WAKE_ON_UNSPECIFIED` | см. README | Профиль пробуждения устройств; см. [server-contract.md](../server-contract.md) §8 |
| `QUOTA_*` | см. README | Дефолты рассчитаны на обычного пользователя |

**NATS `max_payload`.** При `DELIVERY_BACKEND=jetstream` брокер должен
принимать публикацию не меньше `MAX_FRAME_LEN` плюс накладные расходы
конверта. Значение по умолчанию у nats-server — 1 MiB, меньше дефолтного
`MAX_FRAME_LEN` (8 MiB); тогда крупные кадры, принятые нодой, брокер
отвергает, и отправитель получает `INTERNAL`. `max_payload` задаётся
только файлом конфигурации — пример в
[deploy/nats/nats.conf](../deploy/nats/nats.conf) (16 MiB).

## Сеть

- Порт протокола (`BIND_PORT`) — наружу.
- Порт метрик (`METRICS_ADDR`) — **только во внутреннюю сеть.** Метрики
  раскрывают нагрузку, источник ключа и структуру трафика; экспортер не
  требует аутентификации.
- TLS не используется: транспорт шифрует Noise, содержимое сообщений —
  E2E между клиентами. TLS-терминатор перед нодой сломает хендшейк.
- **L4-балансировщик без proxy-protocol скрывает IP клиента.** Тогда
  per-IP лимит хендшейков считает всех одним источником; нода
  proxy-protocol не разбирает, поэтому лимит нужно поднимать.

## Хранилище и бэкапы

Под `STORAGE_PATH` лежат:

| Что | Терять нельзя | Комментарий |
|---|---|---|
| `node_identity_key` | **да** | Потеря — все клиенты с пином отрезаны. Не нужен, если ключ задан `NODE_IDENTITY_KEY` |
| `inbox`, `device_inbox`, `queue_stats` | нет | Недоставленное на прямом бэкенде; потеря — потеря офлайн-сообщений за окно retention. `queue_stats` пересчитывается при старте |
| `queues`, `queue_owner` | нежелательно | Реестр mailbox-очередей; восстановить можно только из бэкапа |
| `device_push_tokens` | нежелательно | Восстанавливается перерегистрацией клиентов |
| `push_state` | нет | Состояние троттлинга пушей |
| `meta` | нет | Архив удалённых из очереди, живёт по retention |

Скрипты [deploy/backup-node.sh](../deploy/backup-node.sh) и
[deploy/restore-node.sh](../deploy/restore-node.sh) рассчитаны на
развёртывание через compose: каталог развёртывания с `data/` и `.env` (в
нём `NODE_IDENTITY_KEY`) и отдельный каталог секретов с кредами FCM/APNs.
Пути задаются переменными `DEPLOY_DIR`, `BACKUP_DIR`, `SECRETS_DIR`
(значения по умолчанию — в начале скриптов, их нужно переопределить под
свою раскладку); `KEEP` — сколько архивов хранить (по умолчанию 7).
`backup-node.sh` проверяет свободное место до архивации и ставится в cron.

Данных JetStream в бэкапе нет намеренно: поток — транспорт с ограниченным
сроком хранения, а не источник истины; восстановление недоставленного из
архива передоставило бы то, что клиенты уже подтвердили.

`restore-node.sh <архив>` отказывается работать при запущенном контейнере
`message-service` (восстановление поверх живой sled её повредит) и
проверяет наличие `.env` в архиве до того, как что-либо менять: данные без
ключа ноды бесполезны. Прежние данные отодвигаются в
`data.before-restore-<время>`. `DRY_RUN=1` только проверяет архив.

Архив снимается с живой базы без остановки ноды. Для sled это
crash-consistent копия: формат журнальный, и при открытии недописанный
хвост отбрасывается так же, как после внезапного выключения.

### Проверка бэкапа

Бэкап проверяется разворачиванием: распаковать архив во временный каталог
и поднять на нём ноду вторым процессом на другом порту, без пушей и
брокера.

```bash
DRILL=$(mktemp -d)
tar xzf <архив> -C "$DRILL"

docker run --rm \
  -v "$DRILL/data:/srv/trust-message/data" \
  -e STORAGE_PATH=/srv/trust-message/data \
  -e BIND_HOST=127.0.0.1 -e BIND_PORT=18099 \
  -e DELIVERY_BACKEND=sled -e PUSH_ENABLED=false -e METRICS_ENABLED=false \
  -e NODE_IDENTITY_KEY="$(grep '^NODE_IDENTITY_KEY=' "$DRILL/.env" | cut -d= -f2-)" \
  <образ> 2>&1 | head -20
```

Признак успеха — строка `node key ready` с тем же `node_key`, что у
рабочей ноды, и отсутствие ошибок хранилища. После проверки удалить
`$DRILL`: в нём лежит секрет ноды.

Ограничения: бэкап, лежащий на том же диске, что и данные, защищает от
удаления каталога, но не от отказа диска — копию нужно уносить с машины.
Полное восстановление требует остановки стека.

## Обновление

1. Прочитать изменения на предмет слома протокола. Смена `protoVersion`
   означает, что клиентов надо обновить **до** ноды: отказ на хендшейке
   симметричен, а окно обновления мобильного приложения длиннее окна
   перезапуска ноды. Правила — [protocol-schema.md](protocol-schema.md).
2. Обновить образ, перезапустить.
3. Проверить в логе `node_key=` — он обязан совпасть с прежним. Если в
   логе `generated a NEW node key`, **немедленно остановить ноду**: том не
   смонтировался, и работа с новым ключом закрепит потерю.
4. Проверить `noise_handshake_total{result="unsupported_version"}` — рост
   означает клиентов на старой версии.

Рестарт рвёт все сессии; клиенты переподключаются сами. По SIGTERM или
SIGINT нода сбрасывает sled на диск и завершается.
Офлайн-очереди переживают рестарт, неподтверждённые конверты JetStream
передоставляются.

## Наблюдаемость

[deploy/docker-compose.override.jetstream.yml](../deploy/docker-compose.override.jetstream.yml)
и [deploy/monitoring/](../deploy/monitoring/) описывают стек: Prometheus
скребёт ноду и node-exporter, правила из
[prometheus-alerts.yml](../deploy/prometheus-alerts.yml) подключены через
`rule_files`, Alertmanager маршрутизирует срабатывания. Канал доставки
алертов задаётся `ALERT_WEBHOOK_URL`; пока он не задан, алерты видны только
в UI Prometheus и Alertmanager.

Проверка, что правила загружены:

```bash
docker exec prometheus wget -qO- http://127.0.0.1:9090/api/v1/rules \
  | grep -o 'trust-message-[a-z]*' | sort -u
```

Логи — `tracing`, уровень через `RUST_LOG` (по умолчанию
`info,sled::config=off`: sled при старте под cgroup-лимитом пишет
сообщение о размере кэша на уровне ERROR). Тело сообщений в логи не
попадает; идентификаторы пользователей (hex `user_id`) и устройств —
попадают. Лимит памяти контейнера ноды стоит задавать явно: sled берёт
размер кэша из cgroup-лимита.

Метрики и алерты — [runbook-metrics.md](runbook-metrics.md).

## Проверка живого развёртывания

```bash
# все сценарии против ноды
bash examples/run_all.sh --message <host:port> --node-key <hex>

# отпечаток ноды: сверить с тем, что роздан клиентам
cargo run --release --example e2e_smoke -- \
  --message <host:port> --scenario probe_tofu --node-key <hex>

# нагрузка (см. runbook-failure-modes.md)
cargo run --release --example load_gen -- \
  --message <host:port> --node-key <hex> --clients 50 --rate 40 --duration 30
```
