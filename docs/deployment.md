# Развёртывание ноды

Что нужно, чтобы поднять ноду и не потерять её ключ. Шаг «забрать ключ и
раздать клиентам» стоит раньше остальных: без него нода работает, но
подключиться к ней по IK никто не может.

---

## Что нужно знать заранее

**Клиент не может подключиться по IK, не зная ключа ноды.** Транспорт —
Noise IK, и ключ раздаётся вне полосы (конфигурация приложения, QR, ручной
пин). Путь первого контакта (Noise XX, TOFU) доверяет ключу, полученному
в момент подключения, — см. [runbook-node-key.md](runbook-node-key.md).

**Терять ключ нельзя.** Пустой том при рестарте означает новый ключ, и все
клиенты с пином отрезаны, хотя метрики доступности остаются в норме.
Обращение с ключом — [runbook-node-key.md](runbook-node-key.md).

## Требования

- Linux, x86-64.
- Диск под `STORAGE_PATH` — офлайн-очереди, push-токены, состояние
  планировщика пушей, реестр очередей, ключ ноды.
- Опционально NATS с JetStream (`DELIVERY_BACKEND=jetstream`).
- Для сборки — только Rust toolchain: схемы компилирует `protox` внутри
  `cargo`, `protoc` не нужен.
- Синхронизация времени (NTP): часы влияют на TTL сообщений, окна
  rate-limit'а и срок подписанного конфига — см.
  [runbook-failure-modes.md](runbook-failure-modes.md).

## Первый запуск

```bash
docker run -d \
  -p 5000:5000 -p 127.0.0.1:9000:9000 \
  -e BIND_PORT=5000 \
  -e METRICS_ENABLED=true \
  -v /srv/trust-message/data:/srv/trust-message/data \
  <образ>
```

1. **Забрать ключ из лога.**
   ```
   WARN generated a NEW node key ... node_key=<64 hex> node_identity_key=<64 hex>
   ```
   Клиентам нужен `node_key` — это X25519-статик. `node_identity_key`
   раздавать не нужно: клиент получает его в подписанном снапшоте и
   проверяет сам.
2. **Сделать бэкап секрета** (`STORAGE_PATH/node_identity_key`) или
   перенести его в `NODE_IDENTITY_KEY` из секрет-менеджера — см.
   [runbook-node-key.md](runbook-node-key.md).
3. **Раздать `node_key` клиентам.**
4. **Проверить, что нода отвечает и подпись конфига проверяется:**
   ```bash
   cargo run --release --example e2e_smoke -- \
     --message <host:port> --node-key <hex> --scenario probe_config
   ```

## Конфигурация: что решить до запуска

Полный список переменных — в [README](../README.md#конфигурация). Здесь —
те, где значение по умолчанию может не подойти.

| Переменная | По умолчанию | Когда менять |
|---|---|---|
| `NODE_IDENTITY_KEY` | — | Задать из секрет-менеджера: ключ переживёт пересоздание тома, потерю диска и переезд на другой хост |
| `DELIVERY_BACKEND` | `sled` | `jetstream` — доставка с `DeliveryAck` и передоставкой |
| `NATS_PUBLISH_TIMEOUT_MS` | `2000` | Короче — быстрее отказ при недоступном брокере; длиннее — только при заведомо медленной сети до NATS |
| `NATS_STREAM_MAX_BYTES` | 350 MiB | Объём потока недоставленного. Политика `discard: new`: при заполнении потока новые конверты получают `FULL` у всех отправителей, принятые не вытесняются. Лимита байт на ящик нет, поэтому значение должно вмещать несколько ящиков, забитых крупными конвертами (кусками медиа). Верхняя граница — свободное место под томом NATS. Ниже текущего заполнения потока не снижать |
| `NATS_MAX_MSGS_PER_SUBJECT` | `10000` | Потолок ящика получателя в конвертах (account-subject и каждый device-subject отдельно); сверх — `FULL` только отправителям в этот ящик. Та же глубина, что `QUOTA_MAX_MESSAGES_PER_QUEUE` у прямого бэкенда |
| `LIMIT_MAX_CONNECTIONS` | `4096` | Потолок открытых соединений — по сути потолок памяти: простаивающая сессия держит около 80 KiB буферов. Поднимать вместе с лимитом памяти контейнера и держать ниже `ulimit -n` с запасом (см. «Сеть») |
| `LIMIT_HANDSHAKE_INFLIGHT_PER_IP` | `32` | **Поднять, если клиенты приходят через общий NAT или L4-балансировщик**: для ноды это один адрес |
| `NOISE_ALLOW_TOFU` | `true` | `false` в закрытом развёртывании: остаются только клиенты с пином |
| `SERVER_CONFIG_TTL_SECONDS` | `86400` | Короче — быстрее вступают в силу изменения конфига; длиннее — терпимее к рассинхрону часов |
| `ADVERTISED_ADDRESS` | пусто | Задать, если нода объявляет свой адрес клиентам |
| `OFFLINE_MESSAGES_RETENTION` | `30d` | Сколько хранить недоставленное на прямом бэкенде |
| `RATE_LIMIT_SEND_MSGS_PER_SEC`, `RATE_LIMIT_SEND_BYTES_PER_DAY` | `100`, 256 MiB | Если клиенты передают медиа частями, файл в десятки мегабайт — это сотни отправок подряд; лимиты нужно поднимать под реальный профиль |
| `PUSH_MIN_GAP_*_MS`, `PUSH_BURST_*`, `PUSH_WAKE_ON_UNSPECIFIED` | см. README | Профиль пробуждения устройств; см. [server-contract.md](../server-contract.md) §8 |
| `QUOTA_*` | см. README | Дефолты рассчитаны на обычного пользователя |

**NATS `max_payload`.** При `DELIVERY_BACKEND=jetstream` брокер должен
принимать публикацию не меньше `MAX_FRAME_LEN` плюс накладные расходы
конверта. Значение по умолчанию у nats-server — 1 MiB, меньше дефолтного
`MAX_FRAME_LEN` (8 MiB); тогда крупные кадры, принятые нодой, брокер
отвергает, и отправитель получает `INTERNAL`. `max_payload` задаётся
только файлом конфигурации — пример в
[deploy/nats/nats.conf](../deploy/nats/nats.conf) (16 MiB).

## Сеть

- Порт протокола (`BIND_PORT`) — наружу.
- Порт метрик (`METRICS_ADDR`) — **только во внутреннюю сеть.** Метрики
  раскрывают нагрузку, источник ключа и структуру трафика; экспортер не
  требует аутентификации.
- TLS не используется: транспорт шифрует Noise, содержимое сообщений —
  E2E между клиентами. TLS-терминатор перед нодой сломает хендшейк.
- **L4-балансировщик без proxy-protocol скрывает IP клиента.** Тогда
  per-IP лимит хендшейков считает всех одним источником; нода
  proxy-protocol не разбирает, поэтому лимит нужно поднимать.
- **TCP keepalive включён по умолчанию** (`TCP_KEEPALIVE_SECS=60`,
  `TCP_KEEPALIVE_INTERVAL_SECS=15`, `TCP_KEEPALIVE_RETRIES=4`):
  соединение, пир которого пропал без FIN, закрывается примерно через
  120 с простоя и освобождает место в лимите сессий пользователя.

### Потолок соединений и дескрипторы

Каждое соединение — дескриптор процесса; кроме них нода держит файлы
sled, соединение с NATS и исходящие HTTPS к провайдерам push.
`LIMIT_MAX_CONNECTIONS` (по умолчанию 4096, `0` — без ограничения) должен
быть ниже `ulimit -n` процесса с запасом под них. Упёршись в лимит
дескрипторов раньше потолка, нода не может принять соединение вовсе:
`accept` получает EMFILE, в логе —
`accept failed; pausing before retry` с `retry_in_ms` (пауза растёт от
100 мс до 1 с и сбрасывается первым успешным `accept`), а соединения
копятся в backlog ядра вместо быстрого отказа.

Прод-override (`deploy/docker-compose.override.jetstream.yml`) задаёт
`LIMIT_MAX_CONNECTIONS=2048` под `mem_limit: 384m` (2048 простаивающих
сессий — около 160 MiB) и `ulimits.nofile` 8192. Поднимать потолок — вместе
с `mem_limit`, не выше `nofile` за вычетом запаса.

Соединения сверх потолка закрываются сразу после `accept`, до
хендшейка, и считаются в
`trust_message_tcp_connection_limit_rejected_total`.

## Хранилище и бэкапы

Под `STORAGE_PATH` лежат:

| Что | Терять нельзя | Комментарий |
|---|---|---|
| `node_identity_key` | **да** | Потеря — все клиенты с пином отрезаны. Не нужен, если ключ задан `NODE_IDENTITY_KEY` |
| `inbox`, `device_inbox`, `queue_stats` | нет | Недоставленное на прямом бэкенде; потеря — потеря офлайн-сообщений за окно retention. `queue_stats` пересчитывается при старте |
| `queues`, `queue_owner` | нежелательно | Реестр mailbox-очередей; восстановить можно только из бэкапа |
| `device_push_tokens` | нежелательно | Восстанавливается перерегистрацией клиентов |
| `push_welcome_claims` | нежелательно | Отметки выданного welcome-пуша; без них аккаунт без токенов при первой регистрации получит приветствие снова |
| `push_state` | нет | Состояние троттлинга пушей и отложенных wake |
| `meta` | нет | Архив удалённых из очереди, живёт по retention |

Скрипты [deploy/backup-node.sh](../deploy/backup-node.sh) и
[deploy/restore-node.sh](../deploy/restore-node.sh) рассчитаны на
развёртывание через compose: каталог развёртывания с `data/` и `.env` (в
нём `NODE_IDENTITY_KEY`) и отдельный каталог секретов с кредами FCM/APNs.
Пути задаются переменными `DEPLOY_DIR`, `BACKUP_DIR`, `SECRETS_DIR`
(значения по умолчанию — в начале скриптов, их нужно переопределить под
свою раскладку); `KEEP` — сколько архивов хранить (по умолчанию 7).
`backup-node.sh` проверяет свободное место до архивации и ставится в cron.
Архив несёт `NODE_IDENTITY_KEY` и креды push, поэтому создаётся с umask
077: сам архив — `0600`, создаваемый этим запуском каталог бэкапов —
`0700`.

Данных JetStream в бэкапе нет намеренно: поток — транспорт с ограниченным
сроком хранения, а не источник истины; восстановление недоставленного из
архива передоставило бы то, что клиенты уже подтвердили.

`restore-node.sh <архив>` отказывается работать при запущенном контейнере
`message-service` (восстановление поверх живой sled её повредит) и до
того, как что-либо менять, проверяет в архиве наличие `.env` (данные без
ключа ноды бесполезны) и ровно одного каталога секретов. Прежние данные
отодвигаются в `data.before-restore-<время>`, текущий `.env` сохраняется
копией `.env.before-restore-<время>` с теми же правами: в нём бывают
значения, которых в архиве ещё нет. Секреты распаковываются в
`SECRETS_DIR` — туда же, откуда их берёт `backup-node.sh`, с теми же
умолчаниями. `DRY_RUN=1` только проверяет архив, включая каталог
секретов.

Архив снимается с живой базы без остановки ноды. Для sled это
crash-consistent копия: формат журнальный, и при открытии недописанный
хвост отбрасывается так же, как после внезапного выключения.

### Проверка бэкапа

Бэкап проверяется разворачиванием: распаковать архив во временный каталог
и поднять на нём ноду вторым процессом на другом порту, без пушей и
брокера.

```bash
DRILL=$(mktemp -d)
tar xzf <архив> -C "$DRILL"

docker run --rm \
  -v "$DRILL/data:/srv/trust-message/data" \
  -e STORAGE_PATH=/srv/trust-message/data \
  -e BIND_HOST=127.0.0.1 -e BIND_PORT=18099 \
  -e DELIVERY_BACKEND=sled -e PUSH_ENABLED=false -e METRICS_ENABLED=false \
  -e NODE_IDENTITY_KEY="$(grep '^NODE_IDENTITY_KEY=' "$DRILL/.env" | cut -d= -f2-)" \
  <образ> 2>&1 | head -20
```

Признак успеха — строка `node key ready` с тем же `node_key`, что у
рабочей ноды, и отсутствие ошибок хранилища. После проверки удалить
`$DRILL`: в нём лежит секрет ноды.

Ограничения: бэкап, лежащий на том же диске, что и данные, защищает от
удаления каталога, но не от отказа диска — копию нужно уносить с машины.
Полное восстановление требует остановки стека.

## Сборка и выкладка скриптом

[deploy/run-deploy.sh](../deploy/run-deploy.sh) синхронизирует рабочую
копию на хост, собирает бинарь на сервере
([deploy/build-message-runtime.sh](../deploy/build-message-runtime.sh)),
раскладывает конфиг мониторинга и правила алертов, пересобирает и
перезапускает стек с JetStream-override, затем сверяет бинарь в контейнере
со свежесобранным и число загруженных Prometheus правил с числом правил в
`deploy/prometheus-alerts.yml`.

- **Цель и значения push.** `SSH_HOST` (обязателен), `SSH_PORT`,
  `DEPLOY_DIR`, `AUTH_IMAGE` и значения push (`FCM_PROJECT_ID`,
  `APNS_KEY_PATH`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID`) берутся
  из окружения, а если там не заданы — из локального `.env` в корне
  репозитория (в git и на сервер он не попадает). Значения push уходят в
  `docker compose` на хосте переменными команды и перекрывают `.env` хоста.
- **Что не уезжает на сервер.** rsync исключает `.git/`, `target/`,
  `.env`, `.env.*`, `/data/`, `/secrets/`, `secret/`, `*.p8`,
  `*firebase-adminsdk*.json`, `node_identity_key`, `.claude/`,
  `coverage.json` и собранный бинарь `deploy/message-runtime/trust_message_tcp`.
  Креды push кладутся на хост отдельно (в прод-override —
  `/root/trust/secrets`). Под `--delete` исключённое на сервере не
  удаляется.
- **Сборка.** `build-message-runtime.sh` собирает дерево, в котором лежит
  сам (`SRC_DIR` по умолчанию — корень этого дерева), в сборочном образе
  `BUILDER_IMAGE` командой `cargo build --release --locked`.
- **Версия тулчейна** задаётся в трёх местах и меняется во всех сразу:
  `FROM` в [Dockerfile](../Dockerfile), `FROM` в
  [deploy/builder.Dockerfile](../deploy/builder.Dockerfile) и тег
  `BUILDER_IMAGE` в `deploy/build-message-runtime.sh`. Сборочный образ
  строится один раз на тег; пересобрать его под прежним тегом —
  `REBUILD_BUILDER=1`.
- **Прежний образ ноды** сохраняется тегом
  `trust-message-service:previous`: откат образа — перевесить его на
  `trust-message-service:jetstream` и `docker compose up -d` (перед этим —
  «Откат» ниже).

## Обновление

1. Прочитать изменения на предмет слома протокола. Смена `protoVersion`
   означает, что клиентов надо обновить **до** ноды: отказ на хендшейке
   симметричен, а окно обновления мобильного приложения длиннее окна
   перезапуска ноды. Правила — [protocol-schema.md](protocol-schema.md).
2. Обновить образ, перезапустить.
3. Проверить в логе `node_key=` — он обязан совпасть с прежним. Если в
   логе `generated a NEW node key`, **немедленно остановить ноду**: том не
   смонтировался, и работа с новым ключом закрепит потерю.
4. Проверить `noise_handshake_total{result="unsupported_version"}` — рост
   означает клиентов на старой версии.
5. Проверить `connection_auth_total{result="unconfirmed"}` — рост означает
   клиентов, которые не подтверждают сессию первым кадром (см. ниже).

Рестарт рвёт все сессии; клиенты переподключаются сами. По SIGTERM или
SIGINT нода сначала закрывает приём соединений, затем сбрасывает sled на
диск (`storage flushed on shutdown`) и завершается; установленные сессии
не дренируются. Офлайн-очереди переживают рестарт, неподтверждённые
конверты JetStream передоставляются.

### Подтверждение сессии клиентом

Нода открывает сессию только по первому кадру клиента после `AuthOk`
([server-contract.md](../server-contract.md) §5). Клиенты обновляются
первыми: `Ping` после `AuthOk` безвреден и для ноды без этого требования.
Клиент, молчащий после `AuthOk`, ничего не получает и отключается через
`SESSION_CONFIRM_TIMEOUT_SECS` (30 с); на ноде это
`connection_auth_total{result="unconfirmed"}` и info-строка
`session not confirmed by the client; closing`.

### Формат хранилища

Офлайн-очереди в формате v3 или v4 нода при старте переписывает в v5
одной транзакцией вместе с маркером формата (лог
`offline queues migrated to storage format v5`); прерванная миграция
оставляет исходный формат, и следующий старт выполняет её заново. На
формате v1 или v2 нода не стартует — см.
[runbook-failure-modes.md](runbook-failure-modes.md), «Формат очередей v1/v2».

### Первый запуск с политикой потока `discard: new`

На старте нода приводит лимиты существующего потока к своему конфигу.
Если у потока другая политика discard:

1. Нода удаляет из потока уже подтверждённые конверты — всё, что не выше
   ack floor её durable-consumer'ов. Лог:
   `removed already acknowledged envelopes before switching the stream to discard-new`
   с `purged=N`. Без этого поток, заполненный доставленным, отказывал бы
   всем новым конвертам, пока те не истекут по возрасту.
2. Сверяет глубину ящиков. Если какой-то ящик уже глубже
   `NATS_MAX_MSGS_PER_SUBJECT`, потолок выставляется по его глубине
   (warn `a mailbox already holds more envelopes than NATS_MAX_MSGS_PER_SUBJECT; ...`
   с `deepest`): иначе JetStream срезал бы старейшие конверты этого ящика.
   Сверка повторяется на каждом старте, пока ящик не разгрузится.
3. Применяет лимиты: лог `applying stream retention limits` со старыми и
   новыми значениями.

После выкатки проверить конфигурацию потока (`nats` — natscli, например из
образа `natsio/nats-box` в сети compose; либо через порт мониторинга NATS
на хосте):

```bash
nats -s nats://nats:4222 stream info messages
curl -s 'http://127.0.0.1:8222/jsz?streams=true&config=true'
```

Ожидается: политика discard — `new`; потолок сообщений на subject —
`NATS_MAX_MSGS_PER_SUBJECT` (или глубина самого полного ящика, если нода
о ней предупредила); `discard_new_per_subject` включён.
`NATS_STREAM_MAX_BYTES` не снижать ниже текущего заполнения потока.

### Откат

**Откат на версию ноды, работающую с потоком по `discard: old`,
опасен.** Такая нода на старте выставляет потоку `discard: old`, оставляя
`discard_new_per_subject`, NATS отвергает эту комбинацию, и нода не
стартует. Перед откатом образа вернуть потоку прежнюю политику:
`discard=old`, `discard_new_per_subject=false`,
`max_msgs_per_subject=-1`:

```bash
nats -s nats://nats:4222 stream edit messages \
  --discard old --no-discard-per-subject --max-msgs-per-subject=-1
```

Флаги сверить с `nats stream edit --help` используемой версии natscli.
Сброс потолка ящика обязателен: под `discard: old` JetStream удаляет
старейшие конверты ящика сверх потолка. После отката переполнение потока
снова вытесняет самые старые конверты, включая недоставленные.

## Наблюдаемость

[deploy/docker-compose.override.jetstream.yml](../deploy/docker-compose.override.jetstream.yml)
и [deploy/monitoring/](../deploy/monitoring/) описывают стек: Prometheus
скребёт ноду и node-exporter, правила из
[prometheus-alerts.yml](../deploy/prometheus-alerts.yml) подключены через
`rule_files`, Alertmanager маршрутизирует срабатывания. Канал доставки
алертов задаётся `ALERT_WEBHOOK_URL`; пока он не задан, алерты видны только
в UI Prometheus и Alertmanager.

Проверка, что правила загружены:

```bash
docker exec prometheus wget -qO- http://127.0.0.1:9090/api/v1/rules \
  | grep -o 'trust-message-[a-z]*' | sort -u
```

Логи — `tracing`, уровень через `RUST_LOG` (по умолчанию
`info,sled::config=off`: sled при старте под cgroup-лимитом пишет
сообщение о размере кэша на уровне ERROR). Тело сообщений в логи не
попадает. На уровне `info` в логе — сводка сессии и события пулов
доставки (hex `user_id`, `deviceId`, счётчики, без собеседников), отказы и
ошибки; строки отказов доставки содержат идентификаторы отправителя и
получателя, строки отказа хендшейка — IP источника. Записи о каждом
сообщении (отправитель, получатель, размер) и IP каждого соединения —
уровень `debug`: `RUST_LOG=debug` включает их вместе с метаданными
переписки. Лимит памяти контейнера ноды стоит задавать явно: sled берёт
размер кэша из cgroup-лимита.

Метрики и алерты — [runbook-metrics.md](runbook-metrics.md).

## Проверка живого развёртывания

```bash
# все сценарии против ноды
bash examples/run_all.sh --message <host:port> --node-key <hex>

# отпечаток ноды: сверить с тем, что роздан клиентам
cargo run --release --example e2e_smoke -- \
  --message <host:port> --scenario probe_tofu --node-key <hex>

# нагрузка (см. runbook-failure-modes.md)
cargo run --release --example load_gen -- \
  --message <host:port> --node-key <hex> --clients 50 --rate 40 --duration 30
```
