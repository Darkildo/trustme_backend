# Протокол агента tmnode и админки, версия 1

Агент `tmnode` связывает хост ноды с админкой
([trustme_admin](https://github.com/Darkildo/trustme_admin)).

**Направление.** Агент всегда звонит сам — исходящими HTTPS-запросами.
На сервере ноды ради управления не открывается ни одного входящего порта.

**Типы.** Описаны в `tmnode/src/protocol.rs`. Админка берёт их из этого
же крейта, поэтому стороны не расходятся.

Все пути начинаются с `/api/v1/agent`; тела запросов и ответов — JSON.

## Подключение: `POST /enroll`

В панели администратор заводит ноду и получает одноразовый токен
подключения `tme_…` (живёт 24 часа). На чистом сервере он запускает:

```bash
curl -fsSL https://raw.githubusercontent.com/Darkildo/trustme_backend/stable/deploy/install.sh \
  | sudo sh -s -- enroll --url https://admin.example.org --token tme_…
```

`install.sh`:
1. ставит Docker, если его нет;
2. скачивает `tmnode` из GitHub Releases и сверяет SHA-256;
3. запускает `tmnode enroll`.

Запрос:

```json
{ "token": "tme_…", "hostname": "srv-1", "arch": "x86_64", "tmnode_version": "0.2.0" }
```

Ответ:

```json
{
  "agent_id": "…",
  "agent_token": "tma_…",
  "node_id": "…",
  "node_name": "Офис",
  "install": {
    "image": "ghcr.io/darkildo/trustme_backend:v0.6.0",
    "public_host": "203.0.113.10",
    "port": 18081,
    "backend": "sled",
    "coturn": {
      "image": "coturn/coturn:4.6.3",
      "realm": "node.example.org",
      "secret": "…",
      "port": 3478,
      "relay_min_port": 49160,
      "relay_max_port": 49200
    }
  },
  "runtime": { "version": "…", "content": "<runtime.toml>" }
}
```

Токен подключения одноразовый: повтор получает `401`.

`node_id` — строка из a-z, 0-9 и `-`, до 64 символов: так его пишет
`node.toml`. `tmnode` приводит его к нижнему регистру (ULID к регистру
нечувствителен). Если id и после этого не подходит, `tmnode enroll`
завершается ошибкой до установки ноды: агент с таким `node.toml` не
работал бы.

Что делает `tmnode enroll`:

1. Сохраняет `agent_token` в `/etc/tmnode/agent.toml` (права 0600).
2. Ставит ноду по `install` (см. ниже) и кладёт `runtime` в каталог её
   данных.
3. Пишет `/etc/tmnode/node.toml` с `management.mode = "managed"` и
   `node.id`.
4. Включает службу `tmnode-agent`.

## Установка

`tmnode install` (без админки) и `tmnode enroll` ставят одно и то же.
Используется только `docker`, без compose.

| Что | Как |
|---|---|
| Сеть | `trustme` |
| Нода | контейнер `message-service`, порт `port:port`, данные в `/var/lib/trustme/node` (владелец — пользователь ноды, uid 10001) |
| JetStream | при `backend = "jetstream"` — контейнер `trustme-nats` |
| coturn | контейнер `trustme-coturn` в сети хоста: диапазон relay-портов через проброс медленный |

**Конфиг coturn** — `/etc/tmnode/coturn/turnserver.conf`.
- Права 0400, владелец — пользователь coturn. Секрет лежит в файле, а не
  в командной строке: её видят `ps` и `docker inspect`.
- Учётки — по общему секрету (`use-auth-secret`), тому же, что в секции
  `[ice]` `runtime.toml` ноды (server-contract.md §6.12).
- Ретрансляция во внутренние сети запрещена (`denied-peer-ip`): иначе
  TURN стал бы входом в сеть сервера.

**Живая нода не затирается.** Если контейнер `message-service` уже есть,
установка останавливается.

## Heartbeat: `POST /heartbeat`

Заголовок `Authorization: Bearer tma_…`. Служба `tmnode-agent` шлёт
heartbeat раз в `interval_secs`. Пределы, которые агент принимает, — от
5 до 3600 секунд.

Запрос:

```json
{
  "tmnode_version": "0.2.0",
  "node_key": "005bdc6b…",
  "report": { "format": "tmnode.report/1" },
  "runtime_status": { "result": "applied", "version": "…", "pending_restart": [] }
}
```

| Поле | Откуда |
|---|---|
| `report` | отчёт `tmnode doctor` (docs/tmnode.md) |
| `runtime_status` | содержимое `runtime.status.json` ноды (docs/runtime-config.md) |

Ответ:

```json
{ "interval_secs": 30, "runtime": { "version": "…", "content": "<runtime.toml>" } }
```

**Желаемые настройки.** Если версия `runtime` отличается от той, что
лежит на диске, агент записывает файл:
- атомарно, с правами 0600, владелец — пользователь ноды;
- нода подхватывает его сама, без перезапуска;
- до записи файл разбирается: документ, который не разбирается, или
  версия в нём не совпадает с объявленной — на диск не попадает.

**Ошибки** агент пишет в журнал службы и повторяет с растущей паузой:
10, 20, 40… секунд, не дольше пяти минут.

## Обновление

С `tmnode` 0.7.0 админка обновляет ноду и сам `tmnode` до версий из
релиза бэкенда. Поля в heartbeat необязательные. Агент до 0.7.0 задание
не видит. Админка до 0.7.0 не видит статуса.

**Версии.** С 0.7.0 версия `tmnode` совпадает с версией релиза бэкенда,
в котором он вышел: в релизе `v0.8.0` и нода, и `tmnode` — 0.8.0. До
этого у `tmnode` была своя нумерация (0.2.0 вышел в `v0.6.0`).

**Задание** приходит в ответе heartbeat:

```json
{
  "interval_secs": 30,
  "runtime": { "version": "…", "content": "…" },
  "update": {
    "id": "01jb…",
    "node_version": "0.8.0",
    "tmnode": { "version": "0.8.0", "sha256": "…" },
    "allow_downgrade": false
  }
}
```

Админка присылает задание в каждом ответе, пока агент не сообщит итог.
Одновременно у ноды не больше одного задания.

**Статус** агент присылает в heartbeat:

```json
{
  "tmnode_version": "0.8.0",
  "node_image": "ghcr.io/darkildo/trustme_backend:v0.8.0",
  "update": {
    "id": "01jb…",
    "state": "succeeded",
    "step": "verify",
    "error": null,
    "started_at": 1792443630,
    "finished_at": 1792443702,
    "from_node_image": "ghcr.io/darkildo/trustme_backend:v0.7.0",
    "node_image": "ghcr.io/darkildo/trustme_backend:v0.8.0",
    "from_tmnode": "0.7.0",
    "tmnode": "0.8.0"
  }
}
```

| `state` | Значение |
|---|---|
| `running` | выполняется; агент шлёт этот статус отдельным heartbeat перед долгими шагами |
| `succeeded` | всё, что просили, стоит и проверено |
| `failed` | не удалось; работает прежняя версия, если в `error` не сказано иначе |
| `rolled_back` | новая нода не прошла проверку, агент вернул прежний контейнер |
| `refused` | агент отказался выполнять задание (условия — ниже) |

Шаги `step`: `check` → `download_tmnode` → `restart_agent` → `pull_image`
→ `recreate` → `verify`. При откате к ним добавляется `rollback`.

**Откуда качать** решает агент, а не админка.
- Образ ноды: `<репозиторий образов>:v<node_version>`. Репозиторий по
  умолчанию — `ghcr.io/darkildo/trustme_backend`. Переопределяется
  переменной `TMNODE_IMAGE_REPO` в юните агента.
- `tmnode`: `<релизы>/v<tmnode.version>/tmnode-<arch>-linux` и
  `SHA256SUMS` рядом.
  Адрес релизов по умолчанию —
  `https://github.com/Darkildo/trustme_backend/releases/download`.
  Переопределяется переменной `TMNODE_RELEASES_URL`.
- Версия `tmnode` совпадает с версией релиза бэкенда, в котором он
  вышел, поэтому релиз — это `tmnode.version`. Задание только на
  `tmnode` от образа ноды не зависит: подходит и для ноды на `:stable`.
- Хэш бинаря должен совпасть дважды: со строкой в `SHA256SUMS` и с
  `tmnode.sha256` из задания.

Поэтому даже захваченная админка не подсунет чужой образ или бинарь. Она
может выбрать только другой выпущенный релиз.

**Когда агент отказывается** (`refused`):
- в `node.toml` нет `management.mode = "managed"`: это явное разрешение
  управлять нодой;
- в `node.toml` стоит `updates.channel = "pinned"`, а `node_version`
  отличается от `updates.version`;
- версия не в формате `X.Y.Z`, `sha256` не 64 hex-символа;
- версия ниже текущей, а `allow_downgrade` не задан;
- задание пустое: нет ни `node_version`, ни `tmnode`.

Совпадение с текущей версией — не отказ: эта часть задания считается
выполненной.

**Порядок.** Сначала обновляется `tmnode`, потом нода: новой ноде может
понадобиться новый агент.

1. `tmnode`. Агент скачивает бинарь во временный файл рядом с текущим
   (`tmnode.new`) и сверяет SHA-256. Затем запускает `<новый> version`:
   версия должна совпасть с заданной. Если всё сошлось, агент сохраняет
   текущий бинарь как `tmnode.prev` и атомарно подменяет файл (rename в
   том же каталоге). Статус `running` со step `restart_agent`
   записывается в `/etc/tmnode/update.json`, после чего агент
   завершается. systemd перезапускает службу (`Restart=always`). Новый
   агент читает `update.json`, сверяет свою версию и продолжает задание.
   Версия не та — итог `failed`.
2. Нода. Агент делает `docker pull` образа, затем читает `docker inspect`
   прежнего контейнера: тома, публикацию портов, сеть, политику
   перезапуска и окружение. Из окружения отбрасывается то, что задано
   самим прежним образом (`Config.Env` образа): так новый образ получит
   свои умолчания. Отбрасываются только пары `KEY=VALUE`, совпавшие с
   образом целиком: значение, переопределённое при запуске, остаётся.
   Дальше агент:
   - останавливает прежний контейнер (`docker stop -t 30`),
     переименовывает его в `message-service.prev` и снимает с него
     политику перезапуска, чтобы Docker не поднял его рядом с новым;
   - создаёт новый с теми же параметрами (`docker create`), подключает
     дополнительные сети и запускает его. Окружение уходит в docker
     файлом `/etc/tmnode/update.env` (0600), а не командной строкой: её
     видит `ps`. Файл удаляется сразу после `docker create`.

   Метки, команда, лимиты ресурсов и healthcheck прежнего контейнера не
   переносятся: их задаёт новый образ. Контейнер, который так не
   перенести (tmpfs, сеть другого контейнера, путь тома с `:`, перевод
   строки в значении окружения), агент не трогает: итог `failed` до
   остановки. Не создался или не запустился новый — прежний
   возвращается, итог `failed`.
3. Проверка, не дольше двух минут: `tmnode doctor` раз в 5 секунд.
   Контейнер должен работать, а ключ ноды остаться прежним: ключ из
   файла совпадает с `endpoint.node_key`. `tmnode doctor` должен пройти
   `endpoint.tcp`, `endpoint.handshake` и `endpoint.config`. Ключ
   сменился — откат сразу, ждать нечего.
   - Проверка прошла: `message-service.prev` удаляется, итог —
     `succeeded`.
   - Не прошла: новый контейнер удаляется, прежний получает своё имя и
     политику перезапуска и запускается, итог — `rolled_back` с причиной
     и хвостом `docker logs` (последние 20 строк, не больше 2 КБ).
     Значения из окружения контейнера в `error` заменены на `***`. Данные
     ноды при откате не восстанавливаются. Если новая версия успела
     изменить их формат, это должно быть сказано в CHANGELOG.

Задание выполняется один раз. Итог по `id` хранится в
`/etc/tmnode/update.json` (0600, без секретов). Повтор того же `id` не
запускает обновление заново, агент только повторяет итог. Статус уходит в
heartbeat, пока админка присылает задание; первый ответ без него — и
агент перестаёт присылать статус.

Агент, который упал посреди шага `recreate`, после перезапуска видит
`running` в `update.json` и сначала восстанавливает рабочее состояние:
есть `message-service.prev`, а нового контейнера нет или он не работает
— значит, нужен откат. Новый работает — проверка доводится до конца.
Упал до пересоздания (`check`, `download_tmnode`, `pull_image`) — нода не
менялась, итог `failed`. Новое задание при незавершённом прежнем
сначала доводит прежнее. NATS и coturn в обновление не входят.

**Без админки** тот же движок запускает `tmnode update` на сервере
(docs/tmnode.md). Он работает только с нодой, у которой в `node.toml`
`management.mode = "local"`: у управляемой ноды один источник правды.
Служба агента и `tmnode update` не работают одновременно — их разводит
блокировка `/etc/tmnode/update.lock`.

**Агенты до 0.7.0** задание не видят. Обновить их можно только на
сервере:

    curl -fsSL https://raw.githubusercontent.com/Darkildo/trustme_backend/stable/deploy/install.sh \
      | sudo sh -s -- agent-upgrade

`install.sh agent-upgrade` ставит `tmnode` последнего релиза и
перезапускает службу `tmnode-agent`.

## Пути

По умолчанию `tmnode` работает в стандартных каталогах:

| Что | Путь | Переменная окружения |
|---|---|---|
| настройки | `/etc/tmnode` | `TMNODE_ETC_DIR` |
| данные ноды | `/var/lib/trustme/node` | `TMNODE_DATA_DIR` |
| юнит агента | `/etc/systemd/system/tmnode-agent.service` | `TMNODE_UNIT_PATH` |

Переопределять их нужно, если нода работает не в Docker — например,
рядом с бинарём, запущенным тем же пользователем.

Владельца файлов (пользователь ноды, пользователь coturn) `tmnode`
меняет, только когда запущен от root. Без root файлы остаются за
текущим пользователем.

## Безопасность

- Адрес админки — только `https://`; `http://` допустим лишь для
  localhost.
- Токен агента хранится только в `/etc/tmnode/agent.toml` (0600) и не
  выводится ни в лог, ни в отладочный вывод. Админка хранит только его
  хэш.
- От админки агент принимает только желаемый `runtime.toml` и задание на
  обновление до выпущенного релиза. Обновление выполняется, только если
  в `node.toml` задано `management.mode = "managed"`. Источники образа и
  бинаря агент выбирает сам (раздел «Обновление»).
