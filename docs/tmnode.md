# tmnode

`tmnode` — утилита обслуживания ноды. Цель — чтобы человек без опыта
администрирования поднимал свою ноду одной командой, а команды и сисадмины
компаний разворачивали парк нод и управляли им через admin-сервис.

Готово:

- **`tmnode doctor`** — проверка ноды только на чтение;
- **`tmnode install`** — нода на чистом сервере одной командой, по
  желанию с TURN;
- **`tmnode enroll` и `tmnode agent`** — подключение к админке и связь с
  ней (протокол — [agent-protocol.md](agent-protocol.md));
- **`tmnode update`** — обновление ноды и самого `tmnode` до версий
  релиза с проверкой и откатом; с админкой то же делает агент.

Два контракта, на которые опираются эти команды и admin-сервис:

- [`node.toml`](#nodetoml-схема-1) — описание ноды;
- [`tmnode.report/1`](#отчёт-tmnodereport1) — машиночитаемый отчёт проверок.

Дальше по плану: `pair` (ссылка и QR для клиента), `backup` /
`restore`.

## Установка ноды одной командой

На чистом сервере Debian или Ubuntu:

```bash
curl -fsSL https://raw.githubusercontent.com/Darkildo/trustme_backend/stable/deploy/install.sh \
  | sudo sh -s -- install --public-host 203.0.113.10 --with-turn
```

Что происходит:

1. `install.sh` ставит Docker, если его нет.
2. Скачивает `tmnode` из GitHub Releases и сверяет SHA-256.
3. `tmnode install` ставит:
   - контейнер ноды из образа `ghcr.io/darkildo/trustme_backend:stable`;
   - с `--with-turn` — coturn и секцию `[ice]` в `runtime.toml`, чтобы
     нода выдавала учётки для звонков;
   - `/etc/tmnode/node.toml`.
4. Печатает адрес, ключ и отпечаток ноды.

Флаги `install`:

| Флаг | Смысл |
|---|---|
| `--public-host` | адрес, по которому к ноде ходят клиенты (обязателен) |
| `--port` | порт ноды (по умолчанию 18081) |
| `--backend sled\|jetstream` | бэкенд доставки; JetStream ставит рядом NATS |
| `--with-turn` | поставить coturn для звонков. Нужны открытые порты 3478/udp+tcp и 49160–49200/udp |
| `--image` | другой образ ноды |

С админкой вместо `install` используется `enroll --url … --token …` —
команду с токеном показывает панель
([agent-protocol.md](agent-protocol.md)).

## Обновление

Нода без админки (`management.mode = "local"` в `node.toml`)
обновляется на сервере:

```bash
sudo tmnode update --node-version 0.7.0                         # только нода
sudo tmnode update --node-version 0.7.0 --tmnode-version 0.7.0  # и сам tmnode
```

| Флаг | Смысл |
|---|---|
| `--node-version X.Y.Z` | образ ноды `ghcr.io/darkildo/trustme_backend:vX.Y.Z` |
| `--tmnode-version X.Y.Z` | новый `tmnode` из релиза `vX.Y.Z`: с 0.7.0 его версия — версия релиза бэкенда |
| `--allow-downgrade` | разрешить версию ниже текущей. Данные при откате не восстанавливаются |
| `--json` | итог в JSON — тот же `UpdateStatus`, что агент шлёт админке |
| `--resume` | только дочитать прерванное обновление |

Что происходит — тот же движок, что у агента
([agent-protocol.md](agent-protocol.md), «Обновление»):

1. Новый `tmnode` скачивается из GitHub Releases. SHA-256 сверяется с
   `SHA256SUMS` релиза, `<новый> version` — с заданной версией. Прежний
   бинарь остаётся как `tmnode.prev` рядом, новый встаёт на его место, и
   обновление продолжает уже он (`tmnode update --resume`). Зависшее
   скачивание (30 с без данных), сбой сети и ответ 5xx повторяются, всего
   до трёх попыток.
2. `docker pull` образа. Pull, который 5 минут ничего не выводит,
   обрывается и повторяется, всего до трёх попыток: скачанные слои Docker
   сохраняет, повтор докачивает остальное по новому соединению. Прежний контейнер останавливается и
   переименовывается в `message-service.prev`. Новый создаётся с теми
   же портами, томами, сетью, политикой перезапуска и окружением — кроме
   переменных, заданных самим прежним образом.
3. До двух минут `tmnode doctor` проверяет новую ноду: контейнер
   работает, ключ прежний, рукопожатие и подписанный конфиг проходят.
   Не прошла — прежний контейнер возвращается, итог «откат» с причиной и
   хвостом `docker logs`.

Ход задания пишется в `/etc/tmnode/update.json`. Прерванное обновление
(сбой питания посреди пересоздания) следующий `tmnode update` сначала
доводит или откатывает.

Код выхода: 0 — обновлено или делать нечего, 1 — отказ, ошибка или
откат, 2 — неверный вызов.

Управляемую ноду так не обновить: `tmnode update` откажет. Её обновляет
агент по заданию из панели.

**Откуда качать** задаёт сервер, не админка: переменные
`TMNODE_IMAGE_REPO` (по умолчанию `ghcr.io/darkildo/trustme_backend`) и
`TMNODE_RELEASES_URL` (по умолчанию
`https://github.com/Darkildo/trustme_backend/releases/download`). У
агента они задаются в юните службы (`Environment=`).

**Агент.** Служба `tmnode-agent` с 0.7.0:
- присылает в heartbeat образ контейнера ноды (`node_image`) и ход
  задания на обновление (`update`);
- выполняет задание из ответа админки. Перед долгими шагами шлёт
  отдельный heartbeat со статусом `running`, а пока шаг идёт — повторяет
  его раз в 30 с: иначе админка сочла бы агента пропавшим;
- после замены своего бинаря завершается, systemd поднимает службу уже
  новым (`Restart=always`);
- при старте сначала дочитывает незавершённое задание.

Агент до 0.7.0 обновляться не умеет. Его обновляют на сервере:

```bash
curl -fsSL https://raw.githubusercontent.com/Darkildo/trustme_backend/stable/deploy/install.sh \
  | sudo sh -s -- agent-upgrade
```

`agent-upgrade` ставит `tmnode` последнего релиза (или
`TMNODE_VERSION=vX.Y.Z`) со сверкой SHA-256. Прежний бинарь сохраняется
как `tmnode.prev`, служба `tmnode-agent` перезапускается. Сам `tmnode`
при этом не запускается, нода не трогается.

## Принципы

Эти правила держат совместимость с будущим admin-сервисом. Ломать их
нельзя.

- **Ядро — библиотека, CLI — оболочка.** Логика в `tmnode/src/*`, `main.rs`
  только запускает её. Агент admin-сервиса вызовет те же функции.
- **Без интерактивных вопросов.** Всё задаётся флагами или `node.toml`,
  поэтому тот же вызов работает из скрипта, cloud-init и агента.
- **Желаемое состояние вместо шагов.** `node.toml` описывает, какой нода
  должна быть. Будущие `install` и `update` приводят машину к этому
  состоянию, и повторный запуск безопасен. `doctor` сообщает о расхождениях
  (`config.drift`).
- **Один источник правды.** Пока `management.mode = "managed"`, локальный
  `tmnode` настройки ноды не меняет.
- **Секретов в выводе нет.** Ни в тексте, ни в JSON. Ключ ноды
  показывается только публичной частью.
- **Конфиг ноды разбирается кодом ноды.** Окружение контейнера проходит
  через `trust_message_tcp::config::from_env_vars`, тот же разбор, что при
  старте ноды. Поэтому `doctor` не расходится с тем, как нода видит свои
  настройки, ни в значениях по умолчанию, ни в ошибках.

## Сборка и запуск

```bash
cargo build --release -p tmnode
# бинарь: target/release/tmnode
```

На хосте ноды (от root: нужен доступ к Docker и к файлу ключа):

```bash
tmnode doctor                 # всё по умолчаниям: контейнер message-service
tmnode doctor --json          # отчёт для скриптов и admin-сервиса
tmnode doctor --config ./node.toml --strict
```

С другой машины проверяется только сеть: открыт ли порт, узнаёт ли нода
пин, подписан ли её конфиг.

```bash
tmnode doctor --remote --addr 203.0.113.10:18081 --node-key <64 hex>
```

| Флаг | Смысл |
|---|---|
| `--config ФАЙЛ` | `node.toml`. Без флага читается `/etc/tmnode/node.toml`, если он есть |
| `--container ИМЯ` | контейнер ноды, перекрывает `runtime.container` |
| `--addr ХОСТ:ПОРТ`, `--node-key HEX` | куда и с каким пином подключаться, перекрывают `endpoint` |
| `--remote` | машина не хост ноды: проверки хоста пропускаются |
| `--json` | отчёт `tmnode.report/1` |
| `--strict` | предупреждения тоже дают код 1 |
| `--timeout СЕК` | предел каждого сетевого шага, 1–120, по умолчанию 5 |

`tmnode config check [ФАЙЛ]` проверяет `node.toml` без проверки самой
ноды.

**Коды выхода:**

| Код | Значение |
|---|---|
| 0 | нода в порядке, предупреждения допустимы (со `--strict` — нет) |
| 1 | есть `fail` или `error` |
| 2 | неверный вызов, отчёта нет |

Где брать адрес и пин, по порядку: флаги → `endpoint` в `node.toml` →
опубликованный порт контейнера на `127.0.0.1` и ключ, выведенный из
секрета ноды. Поэтому на ноде, поставленной без `tmnode`, достаточно
`tmnode doctor` без аргументов.

## node.toml, схема 1

```toml
schema = 1                    # обязательно

[node]                        # метаданные, всё необязательно
name = "Семейная нода"        # до 64 символов
id = "node-01"                # id в парке: a-z, 0-9, '-', до 64
org = "acme"                  # организация в admin-сервисе, тот же формат
labels = { team = "sales" }   # ключ: a-z, 0-9, '-', '_', '.', до 63; значение до 256

[management]
mode = "local"                # local | managed

[endpoint]                    # где нода отвечает клиентам
addr = "203.0.113.10:18081"
node_key = "005bdc6b…"        # публичный X25519-статик (node_key= в логе), 64 hex

[runtime]
kind = "docker"               # в схеме 1 только docker
container = "message-service"
data_dir = "/srv/trust-message/data"   # каталог данных на хосте; по умолчанию из точек монтирования

[delivery]
backend = "jetstream"         # sled | jetstream — ожидаемый бэкенд

[updates]
channel = "stable"            # stable | pinned
# version = "0.5.0"           # обязателен при pinned, запрещён при stable
```

Правила:

- **Строгий разбор.** Незнакомый ключ — ошибка, а не молча пропущенная
  настройка.
- **Версия схемы.** Файл со `schema` новее, чем знает `tmnode`, не
  читается: сообщение просит обновить `tmnode`. Поля добавляются только с
  новой версией схемы.
- **Секретов в файле нет.** Секрет ключа ноды остаётся в
  `STORAGE_PATH/node_identity_key` или `NODE_IDENTITY_KEY`
  ([runbook-node-key.md](runbook-node-key.md)).
- **Пространство под admin-сервис.** `node.id`, `node.org` и метки пока
  только проверяются по форме. `management.mode = "managed"` разрешает
  админке обновлять ноду и запрещает `tmnode update` на сервере.
  `updates.channel = "pinned"` держит версию ноды: задание на другую
  версию агент и `tmnode update` отклоняют.

## Отчёт tmnode.report/1

```json
{
  "format": "tmnode.report/1",
  "tmnode_version": "0.1.0",
  "generated_at": 1792443630,
  "target": {
    "config": "/etc/tmnode/node.toml",
    "container": "message-service",
    "addr": "127.0.0.1:18081",
    "node_key": "005bdc6b…"
  },
  "status": "warn",
  "counts": { "ok": 10, "skip": 2, "warn": 3, "error": 0, "fail": 0 },
  "checks": [
    {
      "id": "host.blob_reserve",
      "status": "warn",
      "summary": "свободно 1.7 ГиБ при резерве 5.0 ГиБ: загрузка файлов получает QUOTA",
      "hint": "расширьте диск или уменьшите BLOB_DISK_RESERVE_BYTES",
      "data": {
        "available_bytes": 1825361100,
        "reserve_bytes": 5368709120,
        "reserve_source": "env",
        "host_path": "…"
      }
    }
  ]
}
```

**Статусы**, от лучшего к худшему:

| Статус | Значение |
|---|---|
| `ok` | всё в порядке |
| `skip` | проверка неприменима или ей не хватило предыдущей; причина в `summary` |
| `warn` | работает, но требует внимания |
| `error` | `tmnode` не смог выяснить ответ (нет прав, нет утилиты) |
| `fail` | нода сломана или сломается |

`status` отчёта — худший из статусов проверок.

**Совместимость.**
- В отчёте всегда есть каждая проверка из таблицы ниже, в том же порядке.
  Неприменимая получает `skip`, поэтому отчёты разных нод сравниваются
  построчно.
- `summary` и `hint` — текст для человека, разбирать его нельзя.
- `id`, `status` и ключи `data` — контракт.
- Внутри `tmnode.report/1` можно добавлять проверки и ключи `data`. Менять
  смысл существующих можно только с новой версией формата.

## Проверки

| id | Что проверяет | Не `ok`, когда |
|---|---|---|
| `config.file` | `node.toml` разобран и прошёл проверку | `fail` — файл неверен; `skip` — файла нет |
| `runtime.docker` | Docker CLI отвечает | `error` — Docker нет или нет прав |
| `runtime.container` | контейнер ноды работает, healthcheck | `fail` — нет, остановлен, `unhealthy`; `warn` — `starting` |
| `runtime.config` | окружение контейнера разбирается как у ноды | `fail` — с таким окружением нода не стартует |
| `config.drift` | нода запущена так, как описано в `node.toml` (бэкенд, порт) | `warn` — расхождение |
| `host.data_dir` | `STORAGE_PATH` вынесен на хост | `fail` — данные и ключ живут в слое контейнера |
| `identity.secret` | секрет ключа на месте и читается | `fail` — нет или повреждён (нода создаст новый ключ); `warn` — права шире 0600; `error` — нет прав прочитать |
| `identity.pin` | ключ совпадает с `endpoint.node_key` | `fail` — не совпадает: клиенты с этим пином не подключатся |
| `host.disk` | свободное место в каталоге данных | `fail` — < 512 МиБ; `warn` — < 2 ГиБ |
| `host.blob_reserve` | место под файлы сверх действующего резерва: `BLOB_DISK_RESERVE_BYTES` из окружения, поверх — `blob_disk_reserve_bytes` из `runtime.toml` (как у ноды, docs/runtime-config.md). `data.reserve_source`: `env` или `runtime`; `runtime_path`, `runtime_error` — если файл есть | `warn` — места меньше резерва, загрузка получает `QUOTA`, или `runtime.toml` не разобран (нода его тоже не применила, резерв по окружению); `error` — `runtime.toml` не прочитать; `fail` — каталог блобов в слое контейнера |
| `host.memory` | память хоста | `warn` — меньше ~90 % рекомендации (sled 512 МиБ, JetStream 1 ГиБ) или почти нет свободной |
| `host.clock` | часы синхронизированы (NTP) | `warn` — нет; от часов зависят сроки сертификатов и подписанного конфига |
| `endpoint.tcp` | порт открыт | `fail` — нет соединения |
| `endpoint.handshake` | Noise IK с пином и вход одноразовым ключом | `fail` — ключ не тот, по адресу не нода или нода отказала во входе |
| `endpoint.config` | подписанный `ServerConfig`: подпись, связь с пином, срок | `fail` — не прошёл проверку |

Сетевые проверки проходят тем же путём, что клиент
(`trust_message_tcp::net::probe`). На ноде остаётся только короткая сессия
случайного ключа.
