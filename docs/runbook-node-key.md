# Runbook: ключ ноды

Ключ ноды — её identity. Он делает две вещи сразу:

- **аутентифицирует ноду перед клиентом** в Noise IK — клиент не может
  подключиться, не зная его публичной части;
- **подписывает снапшот `ServerConfig`** — клиент проверяет подпись и
  сверяет её ключ с тем, которым прошёл хендшейк.

Отсюда главное свойство эксплуатации: **потеря ключа = отключение всех
клиентов до перепиннинга.**

Этот документ — про обращение с ключом: где он лежит, как его бэкапить,
ротировать и по каким сигналам понимать, что с ним что-то не так.

---

## Что это за ключ

| | |
|---|---|
| Тип | **Ed25519 seed**, 32 байта |
| Секрет | `STORAGE_PATH/node_identity_key`, hex, права `0600` |
| Пин | `NODE_IDENTITY_KEY` — hex **секрета**, перекрывает файл |
| Публичный статик (X25519) | выводится из секрета; печатается при старте как `node_key=…` и отдаётся клиенту в `ServerConfig.nodeStaticKey`. **Это то, что знают клиенты** |
| Отпечаток | тот же статик, записанный группами по 4 hex-символа: `A1B2-C3D4-…`. Это форма для сверки глазами, а не хеш — сравнивать нужно строку целиком |
| Публичный identity (Ed25519) | печатается как `node_identity_key=…`; едет в подписанном снапшоте как подписант |

Секрет один. X25519-статик выводится из него birational-отображением —
тем же, каким клиент выводит свой статик из `user_id`. Поэтому клиент
может проверить арифметически, что снапшот подписала **та самая** нода, с
которой он говорит: конверсия identity-ключа обязана дать пин. Второй ключ
пиннить не нужно.

Ключ не связан с ключами пользователей и не участвует в E2E-шифровании
переписки.

## Порядок при первом запуске

1. Поднять ноду. В логе появится:
   ```
   WARN generated a NEW node key; clients pinned to the previous key can no longer connect — expected only on a fresh node  node_key=<64 hex>  node_identity_key=<64 hex>
   ```
   На первом старте это норма (WARN стоит потому, что на живой ноде та же
   строка означает аварию — см. ниже).
2. **Сразу забрать `node_key` из лога** и раздать клиентам: это X25519-статик,
   без него подключиться нельзя. `node_identity_key` раздавать не нужно —
   клиент получает его в подписанном снапшоте и проверяет сам.
3. **Сразу сделать бэкап секрета** — см. следующий раздел.

## Бэкап

Бэкапить нужно **секрет** (содержимое `node_identity_key`), а не публичные
части: публичные выводятся из секрета, обратное неверно.

```bash
# снять
sudo cat /srv/trust-message/data/node_identity_key    # 64 hex-символа

# положить в секрет-менеджер и/или в оффлайн-хранилище
```

Два рабочих подхода:

- **Файл в томе + бэкап тома.** Ключ живёт вместе с очередями; резервируется
  весь `STORAGE_PATH`. Достаточно, если бэкап тома действительно делается и
  проверяется восстановлением.
- **Пин через `NODE_IDENTITY_KEY`** (рекомендуется для прода). Секрет хранится
  в секрет-менеджере и подаётся переменной окружения. Тогда пересоздание
  тома, переезд на другой хост и потеря диска не меняют identity ноды.
  Файл в этом случае не читается вовсе.

Проверка восстановления (делать до того, как понадобится):

```bash
NODE_IDENTITY_KEY=<hex-из-бэкапа> STORAGE_PATH=/tmp/probe cargo run --release
# в логе: node key pinned from NODE_IDENTITY_KEY  node_key=<та же публичная часть>
```

Если `node_key` в логе совпал с прежним — бэкап валиден. Секрет,
переданный в командной строке, попадает в историю shell и список
процессов; после проверки его стоит оттуда убрать, а `/tmp/probe` удалить.

## Ротация

Ротация ключа — **ломающая операция**: каждый клиент должен получить новый
пин, иначе перестанет подключаться. Плановый порядок:

1. Сгенерировать новый секрет:
   ```bash
   openssl rand -hex 32
   ```
2. Узнать его публичную часть, не трогая прод: поднять ноду с этим секретом
   и пустым `STORAGE_PATH` (см. «Проверка восстановления») и снять
   `node_key` из лога.
3. Раскатать новую публичную часть клиентам **заранее** (обновление
   приложения / рассылка пина), с окном на обновление.
4. Только после этого подменить `NODE_IDENTITY_KEY` (или файл) и
   перезапустить ноду.
5. Проверить `node_key=` в логе и `trust_message_tcp_node_key_source`.

Одновременно два ключа нода держать не умеет: IK-респондер отвечает одним
статиком. Если нужен переход без разрыва — это делается на уровне двух
инстансов за разными адресами, а не внутри одной ноды.

**Внеплановая ротация (ключ утёк):** порядок обратный — ключ меняется
немедленно, клиенты отваливаются и чинятся обновлением пина. Утечка секрета
означает, что кто-то может выдавать себя за ноду перед клиентами, у которых
старый пин, **и подписывать от её имени конфиг**.

## Первый контакт (TOFU)

Клиент без пина может подключиться по XX: ключ ноды приезжает в ходе
хендшейка. Что это значит эксплуатационно:

- **Доверие устанавливается на первом контакте.** Активный MITM именно в
  этот момент подменяет ноду, и клиент этого не заметит — заметить можно
  только сверив отпечаток вне полосы. Публиковать отпечаток там, где
  пользователь может его сверить, — работа оператора.
- **`NOISE_ALLOW_TOFU=false` закрывает этот путь целиком.** Остаются только
  клиенты с пином; новый клиент без ключа подключиться не сможет вовсе.
  Разумно для закрытых развёртываний.
- **Доля XX видна в метрике.** `noise_handshake_total{pattern="xx"}` — это
  подключения, доверие в которых не проверено пином. Всплеск на зрелом
  развёртывании означает либо волну новых установок, либо что клиенты
  потеряли пин.

Снять отпечаток живой ноды и сверить его с раздаваемым:

```bash
cargo run --example e2e_smoke -- \
  --message <host:port> --scenario probe_tofu --node-key <ожидаемый hex>
```

Без `--node-key` сценарий просто печатает отпечаток; с ним — проверяет
совпадение и падает при расхождении.

## Подписанный `ServerConfig`

Снапшот конфигурации подписывается этим же ключом и живёт
`SERVER_CONFIG_TTL_SECONDS` (по умолчанию сутки). Практические следствия:

- **Срок обязателен.** Ноль запрещён конфигурацией: подписанный конфиг без
  срока — вечно предъявляемая запись, которую нечем отозвать.
- **Часы имеют значение.** Клиент отвергает просроченный снапшот, поэтому
  ушедшие вперёд часы ноды выдают снапшоты «из будущего», а ушедшие
  назад — сразу просроченные. NTP на ноде обязателен.
- **Смена ключа обесценивает выданные снапшоты** — они перестают проходить
  проверку связи с новым статиком. Отдельного отзыва не нужно.
- `ADVERTISED_ADDRESS` попадает под подпись. Пустое значение означает
  «нода адрес не объявляет»; ставить туда неверный адрес хуже, чем не
  ставить никакого.

## Сигналы и что они означают

| Сигнал | Что означает | Что делать |
|---|---|---|
| `trust_message_tcp_node_key_source{source="generated"} == 1` **на живой ноде** | Файла ключа не было — прежний потерян (том пересоздан, каталог не смонтирован). Все клиенты отрезаны | Остановить ноду, вернуть секрет из бэкапа, перезапустить. Не давать ноде работать с новым ключом — это закрепит потерю |
| `source="file"` | Нормальный режим без пина | — |
| `source="configured"` | Ключ пришёл из `NODE_IDENTITY_KEY` | — |
| `trust_message_tcp_node_key_permissions_ok == 0` | Файл ключа читаем не только владельцем | `chmod 600`, разобраться, кто имел доступ; при сомнениях — считать утечкой и ротировать |
| Старт падает с `node key … is malformed` | Файл повреждён | Восстановить из бэкапа. Нода **намеренно** не генерирует новый ключ молча |
| Всплеск `trust_message_tcp_noise_handshake_total{result="rejected"}` | Клиенты приходят со старым/чужим пином | Сверить `node_key` в логе с тем, что раздан клиентам; проверить, не было ли незапланированной ротации |
| Рост доли `pattern="xx"` | Клиенты подключаются без пина (первый контакт) | Норма при волне новых установок; на зрелом развёртывании — признак того, что пин теряется |
| `result="tofu_disabled"` | Клиент пришёл по XX, а нода его не принимает | Ожидаемо при `NOISE_ALLOW_TOFU=false`; клиентам нужен ключ вне полосы |
| Всплеск `result="unsupported_version"` | Клиенты говорят на другой версии протокола | Сверить версии; см. docs/protocol-schema.md |
| `result="bad_magic"` | В порт стучится не наш протокол (сканер) или очень старый клиент | Само по себе не авария; смотреть на источник |

Минимальные алерты, которые стоит завести:

```
# ключ сгенерирован заново на ноде, которая уже работала
trust_message_tcp_node_key_source{source="generated"} == 1

# права разъехались
trust_message_tcp_node_key_permissions_ok == 0

# нода перестала пускать клиентов
rate(trust_message_tcp_noise_handshake_total{result="rejected"}[5m]) > <порог>
```

## Частые ошибки

- **Смонтировать пустой том и перезапустить.** Нода сгенерирует новый ключ и
  продолжит работать — с точки зрения графиков «всё зелено», а клиенты не
  подключаются. Отсюда WARN и метрика источника.
- **Забэкапить публичную часть вместо секрета.** Публичные части
  восстанавливаются из секрета, обратное неверно.
- **Ротировать ключ до раскатки пина клиентам.** Порядок всегда: сначала
  клиенты знают новый ключ, потом нода начинает им пользоваться.
- **Положить секрет в `docker-compose.yml` в репозитории.** Файл попадает в
  git и в образ; для пина есть переменная окружения и секрет-менеджер.
- **Оставить ноду без синхронизации времени.** Подписанный конфиг имеет
  срок; разъехавшиеся часы ломают его проверку на стороне клиента.
